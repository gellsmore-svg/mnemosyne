### Code inspection (`src/mnemosyne/adapters/embedding.py`, `config.py`, `config.example.yaml`)

**Confirmed how `local_command` actually runs:**

- `LocalCommandEmbeddingAdapter.embed(text)` calls `subprocess.run(self.command, input=payload, ...)` *once per node* — i.e., **a fresh process per embed call** (line 204 of `embedding.py`). No persistent worker, no batching, no stdin loop.
- `payload = json.dumps({"model": self.model, "text": text})` over stdin.
- Output JSON accepts `{"vector":[...]}`, `{"embedding":[...]}`, or
  Ollama-style `{"embeddings":[[...]]}`.
- The Python side `l2_normalize`s the returned vector — the local model
  does not need to pre-normalise.
- Timeout reuses `runtime.ollama_timeout_seconds` (default 180s). For a
  per-node spawn this is fine for any reasonable embedding model.
- HTTP-backed adapters are policy-blocked unless
  `runtime.allow_http_ingestion_adapters: true` (line 244–254).
- For non-mock adapters, the stored vector dimension is **discovered from
  the model's output** (line 187) — not driven by
  `runtime.embedding_dimensions`. Switching from the 16-dim mock to a
  real 384-dim model therefore forces a rebuild of all stored profiles.

**Runtime config schema** (`src/mnemosyne/config.py`):

### Proposal for task 46 (test/choose the local profile adapter)

The development plan's "Phase A remaining work" reads: *"Choose and
configure the actual local model-backed profile command, then validate
candidate quality against a refreshed corpus."* The adapter framework is
already shipped. What is missing is **(a)** a chosen model + helper, and
**(b)** an evaluation that the chosen model produces useful candidates.
Nothing here calls for changing the adapter or the candidate-review

#### Decision matrix

Constraints from architecture / requirements:

- Local non-HTTP (Local Memory Interface Boundary).
- Deterministic: same text → same vector (the review queue assumes stable
  similarities; non-determinism would generate review churn).
- Cheap enough to run on the operator's 8GB RAM + GTX 3060 mobile
  (ADR-013, DQ-006). CPU-fast preferred since the GPU may be in use.
- Quality good enough that, on AMS-style philosophical/theological prose,
  the top-k similar nodes look semantically related to a human reviewer.
- Compatible with the existing per-process subprocess invocation. (If we
  later want batching/persistence, that is a separate, named slice.)

**Candidate models, ranked by suitability for the first test:**

| Rank | Model | Dim | Disk | Why for this task |
|---|---|---|---|---|
| 1 | `BAAI/bge-small-en-v1.5` | 384 | ~130 MB | Strong English retrieval scores; deterministic; no query/passage prefix needed for symmetric similarity; widely used and trusted. |
| 2 | `sentence-transformers/all-MiniLM-L6-v2` | 384 | ~80 MB | Smallest mainstream sentence-transformer; CPU-fast; the classic baseline; very deterministic. |
| 3 | `intfloat/e5-small-v2` | 384 | ~130 MB | Strong retrieval; requires `passage:` / `query:` prefix discipline, which is friction we don't need yet. |

**Diagnostic-only (would breach the HTTP boundary if used as the
production path):** `nomic-embed-text` via Ollama (it's already there as
`ollama_http` and policy-blocked).

**My recommendation: start with `BAAI/bge-small-en-v1.5`**, fall back to
MiniLM if `bge-small` is awkward to set up.

#### Helper script (Path A — does not touch codex code)

The adapter contract is already specified: read stdin JSON, write stdout
JSON. The simplest helper that satisfies it without touching the existing
adapter code:

```
tools/profile_helper.py
  - reads one JSON object on stdin: {"model": "...", "text": "..."}
  - loads model (lazily, but per-process — cost paid per call)
  - emits {"vector": [...]} on stdout
  - returns nonzero on any failure
```

Two implementation choices for the helper:

**(a) `sentence-transformers` (PyTorch)**. Familiar, easy to install in
the existing `.venv`. Per-process load is ~1.5–3 s for `bge-small-en-v1.5`
on CPU. With Mnemosyne's per-call spawn, full AMS backfill (~176k nodes)
would take roughly 4–8 days wall clock at this rate. Sufficient for a
quality check on a small subset; not yet feasible for whole-corpus
backfill.

**(b) `fastembed` (ONNX-runtime backed)**. Same models exposed via a much
faster cold start (~200–400 ms). Whole-AMS backfill would drop to
something like 12–20 hours at the cost of one extra dependency. **This is
my recommended path for the helper** unless there is an existing
preference against `fastembed` in the project.

Either way: the helper lives in `tools/` (or a separate user-owned
location) and the framework code does not change.

#### Path B (deferred, requires adapter change)

If the wall-clock cost of per-call spawning becomes blocking, the right
next step is to extend `LocalCommandEmbeddingAdapter` so it can keep a
long-running subprocess and exchange newline-delimited JSON
requests/responses. This is the same `local_command` contract extended to
streaming, behind a small flag. Per-call cost drops from ~200 ms (Path A)
to ~5–15 ms (embedding only). Backfilling 176k nodes then takes minutes,
not days.

This is a directly load-bearing change to the file codex has been editing,
so I would not start it without explicit user/codex approval, and it
should land as its own commit on top of `3de72fc`.

#### Drift check 1: does `backfill-embeddings` respect ingestion epochs?

Chain: CLI → `process_embedding_backfill_batches` → `process_next_embedding_backfill_job` → `backfill_node_embeddings` → `embedding_backfill_node_query` (in `src/mnemosyne/db/repositories.py:940`).

```python
query: dict[str, Any] = {"status": {"$ne": "superseded"}}
```

**Result: clean.** Backfill excludes superseded nodes by default. Only active-epoch nodes get profiles generated. Wasted compute on old-epoch nodes is not possible through this path.

The query also filters `embedding.vector: {$exists: False}` when `force=False`, so missing-profile mode skips nodes that already have a vector. With `force=True`, it rebuilds every active-status node.

#### Drift check 2: is FastAPI shaped as a memory API or UI-coupled?

42 endpoints in `src/mnemosyne/web/app.py`. Read-path endpoints follow a consistent thin-passthrough shape:

```python
@app.get("/api/documents")

    return {"ok": True, "documents": list_documents(db, limit=limit)}
```

Almost every GET endpoint is a one-line lift of an underlying memory function returning `{"ok": bool, "<key>": <data>}`.
