# Lifecycle Next Phase Requirements

Date: 2026-05-29

Status: planning and implementation-direction document. This captures the next phase requirements supplied during development. The current repository/package name remains `Mnemosyne`; `Lifecycle` is used here as the product/system direction until a deliberate rename is chosen.

## Overview

The next phase should improve transparency, quality, and usability across three linked tracks:

1. Real-world human experimentation through a better UI.
2. Higher-quality ingestion and processing of new material.
3. A stronger core memory engine for semantic retrieval, chronology, relationshiping, inference, and governance.

Quality is more important than speed for the foreseeable future. The system should favour better embeddings, reasoning, context construction, source interpretation, and inference quality even when processing takes longer.

## Repository Refresh

The current repository contains material generated by earlier prototypes. Existing generated summaries, inferred relationships, and supporting content may be obsolete because they predate the current semantic, graph, process-run, active-document, and governance scaffolds.

The repository should be treated as reproducible from source documents.

Required operating model:

```text
Source Documents
  -> Fresh Ingestion
  -> Semantic Analysis
  -> Relationship Construction
  -> Inference Generation
  -> Repository Build
```

The system needs a controlled mechanism to:

- clear disposable generated repository content;
- re-ingest all source content from scratch;
- rebuild semantic relationships;
- rebuild inferred content;
- rebuild supporting node structures;
- make each rebuild auditable and reproducible.

Future rebuilds should use ingestion epochs so later content already in the system can be superseded or compared against a fresh chronological build.

Example:

```text
ingestion_epoch: 2026-05-29-rs5-rebuild-001
```

## Full LLM Transparency

Transparency should become a first-class feature. Users should be able to understand how outputs were produced without reading Python or inspecting raw database records.

The system should expose structured, human-readable activity reports for:

- ingestion;
- context construction;
- response generation;
- internet-assisted reasoning;
- repository rebuilds.

These reports should explain system behaviour, not merely debug implementation details.

## Ingestion Activity Reports

Every ingestion operation should produce a concise human-readable log.

Recommended sections:

- Source Analysis:
  - document identified;
  - metadata extracted;
  - earliest credible creation/publication date determined;
  - topics identified;
  - entities identified.
- Semantic Processing:
  - concepts detected;
  - relationships detected;
  - nodes created;
  - existing nodes updated or linked.
- Repository Actions:
  - new content created;
  - existing content merged;
  - inferences generated;
  - epoch/rebuild metadata recorded.
- LLM Activity:
  - number of LLM calls;
  - purpose of each call;
  - reason for additional calls;
  - whether any call failed or was retried.
- System Actions:
  - function name;
  - purpose;
  - high-level result.

Example:

```text
Function: Extract Metadata
Purpose: Determines authorship, dates, and document properties.

Function: Build Semantic Relationships
Purpose: Connects concepts to existing knowledge.

Function: Generate Inferences
Purpose: Produces knowledge that is implied but not explicitly stated.
```

## Context Construction Reports

Question answering should not be a black box. Each answer flow should expose a context construction report.

Recommended sections:

- Query Understanding:
  - what the system believes the user is asking;
  - key concepts extracted;
  - related entities identified.
- Retrieval Activity:
  - nodes retrieved;
  - why they were selected;
  - relevance/diagnostic scores;
  - identity or trust filters applied.
- Context Expansion:
  - related content discovered;
  - supporting documents selected;
  - adjacent/path/semantic candidates included.
- LLM Activity:
  - number of calls;
  - purpose of each call;
  - whether recursive or iterative reasoning occurred.
- System Functions:
  - high-level descriptions of important operations.

Example:

```text
Function: Retrieve Related Nodes
Purpose: Finds semantically similar or lexically relevant content.

Function: Context Expansion
Purpose: Broadens the search to related concepts and graph neighbours.

Function: Evidence Ranking
Purpose: Orders information by relevance and diagnostic quality.
```

## Response Generation Reports

The final response phase should explain how the answer was assembled.

Recommended sections:

- Evidence Used:
  - contributing sources;
  - contributing nodes;
  - key concepts.
- Reasoning Steps:
  - information combined;
  - contradictions or uncertainty handled;
  - supporting evidence prioritised.
- LLM Activity:
  - calls made;
  - purpose of each call;
  - whether additional reasoning cycles occurred.
- Final Assembly:
  - how the final answer was constructed;
  - what was omitted due to uncertainty, budget, or lack of evidence.

## Internet-Assisted Reasoning

The system should be able to use the internet as temporary context when the local corpus is insufficient.

Desired workflow:

```text
User Question
  -> Initial Reasoning
  -> Determine Internet Needed?
  -> Internet Retrieval
  -> Context Enrichment
  -> Additional LLM Pass
  -> Final Response
```

The LLM or planner should be able to decide:

- whether internet access is required;
- what information should be retrieved;
- whether retrieved information should remain temporary;
- whether retrieved information should become candidate knowledge;
- whether candidate knowledge is eligible for permanent ingestion.

Internet-derived content must not automatically become trusted repository content.

Allowed states:

- Temporary Context: used only for the current answer.
- Candidate Knowledge: stored separately for review.
- Permanent Knowledge: ingested only after passing defined criteria.

This prevents contamination of durable memory with low-quality, unstable, or unreviewed web content.

## Chronological Ingestion

Large corpus ingestion should preserve historical development order where possible.

The RS5 Clause collection is the first major test case.

The system should determine the earliest credible origin date for each document and ingest documents from earliest to latest.

Date priority:

1. Explicit date inside document content.
2. Date embedded in filename.
3. Original file creation date, when preserved by the source acquisition path.
4. Original file modification date, when preserved by the source acquisition path.

The earliest credible origin date should generally win.

Filesystem timestamps are weak fallback evidence. They may represent copy/import time rather than authorship time, especially for web-staged uploads or copied corpora.

Example:

```text
Document date: 2020
Filename date: 2026
File creation date: 2026

Result: 2020
```

Chronological ordering matters because the user needs to interrogate how ideas developed over time, not only their latest form.

## Multi-Corpus Interrogation

The system should support interrogation across at least two major domains.

### Domain A: Relational Substrate / AMS / RS Corpus

The system must ingest and reason over:

- AMS content;
- Relational Substrate content;
- RS5 Clause folder content;
- related supporting documents.

The ingester should handle large file collections, determine likely historical order, and ingest from earliest to latest.

Purpose:

- interrogate the development of ideas over time;
- compare early and later formulations;
- detect conceptual drift, refinement, contradiction, and continuity.

### Domain B: Product/System Self-Awareness

The system should also maintain awareness of its own product, design, implementation, process, and governance state.

This includes:

- architecture decisions;
- requirements;
- implementation status;
- roadmap;
- known gaps;
- review findings;
- process runs;
- restart/continuity state.

The user should be able to ask what the system is, what it knows, what has changed, why a design choice exists, and what remains unresolved.

## Historical Rebuild And Existing Later Content

The system must define behaviour when later content was already ingested before earlier content is discovered.

Recommended model:

- assign every major ingestion/rebuild run an ingestion epoch;
- preserve source identity and chronology metadata;
- allow repository refreshes to rebuild derived content under a new epoch;
- distinguish current active epoch from archived/superseded epoch data;
- avoid silently merging incompatible derived relationships across epochs.

This supports reproducibility without pretending earlier prototype-derived inferences are authoritative.

## Human-Centred Design Goal

The system should increasingly explain itself.

The objective is not merely to answer questions. It is to let users understand:

- what the system knows;
- why it knows it;
- how it reached conclusions;
- what internal decisions were made;
- what evidence was used;
- what uncertainty remains;
- what should be reviewed before becoming durable knowledge.

Users should be able to develop a clear mental model of system behaviour over time.

## Implementation Implications

Near-term implementation should prioritise:

1. Human-readable activity report structures for ingestion and answer flows.
2. UI surfaces that show context construction and response generation reports.
3. Chronology extraction and ordering utilities for large source collections.
4. Ingestion epoch schema and rebuild controls.
5. Internet temporary-context and candidate-knowledge boundaries.
6. Higher-quality ingestion adapters and LLM-driven semantic extraction.
7. Multi-corpus organisation and corpus/domain filters.
8. Product self-awareness queries over requirements, roadmap, commits, reviews, and process state.

## Non-Goals For Immediate Implementation

The next phase should not immediately grant autonomous write authority to LLM agents.

Internet content, inferred relationships, generated summaries, and cross-corpus inferences should remain reviewable until trust, chronology, process, and provenance controls are strong enough to support higher autonomy.
